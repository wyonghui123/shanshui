配音深化研究：情感 · 抑扬顿挫 · 性别匹配

针对《静夜思》配音原型「无情感、无抑扬顿挫、性别未定」三个缺口的专项技术研究

方法：三条并行证据线（韵律控制技术路径 · 性别与音色语义 · 工程落地与成本）→ 交叉验证 → 落地建议。置信标注：[CONFIRMED] 多源 / [SINGLE-SOURCE] 单源 / [unverified] 未核实。
摘要

三个缺口的诊断结论

三条缺口的可解程度差别很大——一个易解、一个半解、一个触及行业天花板。

情感
● 可解

商业 TTS 已成熟。Azure mstts:express-as、MiniMax emotion、CosyVoice instruct 都提供情感风格，且可做到逐句指定——足以表达《静夜思》的起承转合。

抑扬顿挫
● 半解（句级可，逐字难）

句级起伏现成可用（Azure SSML 的 pitch/contour/break/emphasis）；但逐字平仄——五言诗每个字单独定音高与时长——没有任何商用 API 支持。

性别匹配
● 可解

男声资源充足，且 Azure 有专门的中文「诗人」风格男声（Yunyi 的 poet style）。性别语义上「第一人称诗宜用诗人自己的声音」成立。

关键约束

「逐字抑扬顿挫」是当前行业天花板。Azure 官方文档明确说明：pitch contour「不适用于单个单词和短短语，建议在整句或长短语上调整」。也就是说，市面上最完整的韵律控制 API，也无法直接给五言诗的每个字指定平仄音高。[cite:2]

诊断

原型的扁平听感不是参数没调好，而是架构天花板：Web Speech API 的 SpeechSynthesisUtterance 只暴露 rate / pitch / volume 三个整句级属性，且不支持自定义 SSML（不支持的标签会被剥离）。[cite:1]

01

诊断：为什么原型的听感是扁平的

Web Speech API 的能力边界

能力支持情况说明
语速 rate整句级一个 utterance 一个值
音高 pitch整句级同上，无法逐字变化
音量 volume整句级同上
停顿 / 重音不支持无 <break> / <emphasis>
情感风格不支持无 style / emotion 参数
SSML实质不支持MDN：可传 SSML 文本，但不支持的标签会被剥离[cite:1]

结论：原型只能做「四句之间语速/音高略有差异」，做不到句内的起伏，也做不到情感着色。要突破，必须离开 Web Speech API。CONFIRMED

02

缺口一：情感 — 可解，且可逐句

情感控制已成熟，关键在于粒度：句级情感足以支撑《静夜思》的起承转合。

可用的情感控制接口

平台接口可用风格（节选）粒度
Azure mstts:express-as style=... poetry-reading、sad、sentimental、lonely、whispering、empathetic、depressed、serious、narration-relaxed 句 / 段级
MiniMax emotion 参数 happy、sad、angry、fearful、disgusted、surprised、calm utterance 级
CosyVoice instruct 文本指令 如「你正在进行诗歌朗诵，你说话的情感是 neutral」；v3-flash 男声支持 sad / fearful / happy 等 句级（指令式）
ElevenLabs v3 audio tags [sighs]、[whispers]、[sad]、[slow]、[pauses] 标签级（定性）

Azure 与 CosyVoice 支持把风格标签分别套在每一句上，因此《静夜思》可以做「起句 neutral → 承句 lonely/sad → 转句稍扬 → 合句 sad/depressed」的句级情感弧。[cite:2][cite:3][cite:5][cite:10]

已知风险

有社区报告称 Azure 中文语音的 mstts:express-as styles 与副语言标签在部分音色下可能「无论怎么设输出都一样」，且部分标签未生效。这是社区报告而非官方定论，但意味着情感风格必须逐音色实测，不能只看文档列表。[cite:2]

03

缺口二：抑扬顿挫 — 句级可解，逐字触顶

这是三个缺口里最难的一个。必须先区分两个不同层次的「抑扬顿挫」。

先把问题拆开：两种抑扬顿挫

层次含义技术需求现成可用？
句级起伏 四句之间有高低、快慢、轻重、停顿的变化 句级 pitch / rate / break / emphasis ✓ Azure SSML 完整支持
逐字平仄 五言诗每个字按平仄单独定音高与时长（平长仄短、句末拖腔、入声短促） 每字 pitch + duration 独立控制 ✗ 无商用 API 支持

你听到的「没有抑扬顿挫」，一部分是原型连句级起伏都没有（Web Speech API 限制）；另一部分——真正意义上的「韵味」——属于逐字平仄，那是另一道门槛。

天花板在哪里：Azure contour 的官方限制

「Pitch contour doesn't work on single words and short phrases. It's recommended to adjust the pitch contour on whole sentences or long phrases.」 — Azure 语音合成 SSML 文档 [cite:2]

Azure 的 <prosody contour="(0%,+20Hz) (10%,-2st) (40%,+10Hz)"> 是目前商用 API 中最接近「抑扬顿挫」的能力——它能沿时间轴画出音高曲线。但官方明确说它只对整句/长短语有效，不能对单个字生效。因此无法直接写出「床（+2st）前（0）明（+1st）月（-3st）光（+4st，拖长）」这样的逐字平仄谱。CONFIRMED

逐字平仄的三条可能路径

路径做法可行性风险
A. 逐字合成 + 拼接 把每个字单独合成（各自指定 pitch/rate），再按平仄时长拼接 工程可行 字间过渡生硬、气息断裂，可能比扁平更难听
B. 后处理改韵律 先合成整句，再用声学工具（如 Praat / WORLD 声码器）改写音高与时长曲线 技术可行 需自研工具链；处理不当会产生机械感/颤音伪影
C. 诗歌专用合成模型 用 Intoner（Chinese Poetry Intoning Synthesis，IJCAI 2025）这类从格律出发、字符级控制旋律与时长的扩散模型 最对口但不可用 仍是研究论文，未开放为 API 或可下载模型[cite:4]

ChatTTS 的 [break_0-7] / [oral_0-9] 只能控制停顿与口语化程度，不涉及音高，不能承担平仄。[cite:16]

判断

句级抑扬顿挫：现成可用，Azure SSML 即可做到，配合逐句情感标签，已能明显改善听感。逐字平仄：没有任何开箱方案——要么自研后处理（路径 B，风险中等），要么等 Intoner 类模型开源，要么改用真人吟诵采样（唯一真正有「韵味」的来源）。

04

缺口三：性别与音色匹配

男声资源充足；关键不是「有没有男声」，而是「哪种气质的男声配得上留白的人物」。

中文男声候选（含情感风格）

平台音色可用风格 / 气质与《静夜思》的匹配度
Azure zh-CN-Yunyi:DragonHDFlashLatestNeural poet、game-narrator、captain、cavalier、geomancer 最高——唯一带「诗人」风格的音色
zh-CN-Yunhan:DragonHDFlashLatestNeural sad、lonely、whispering、empathetic、tired 很高——孤独 + 低语，正是静夜气质
zh-CN-YunxiNeural narration-relaxed、sad、depressed、serious 中——通用旁白，偏平实

音色清单与风格字段来自各平台官方语音列表文档。[cite:3][cite:6][cite:8][cite:10]

语义层：这该是谁的声音？

《静夜思》是第一人称抒情诗，「我」即李白。配音有两种定位：

  • 诗人自己的声音——强化「李白夜思故乡」的第一人称沉浸感，与「背影剪影、无五官」的画面设计同构（画面不画脸，声音给身份但不给五官）。
  • 叙述者 / 吟诵者的声音——客观呈现，适合朗诵会、配乐诗朗诵。

检索到的资料（朗诵教学、音乐朗诵会评述）显示，中文古诗朗读的性别选择更多与作品气质、角色分配相关，而非固定惯例——例如《中国唐宋名篇音乐朗诵会》中《雨霖铃》《声声慢》用女声，《长恨歌》由男声与女声分读。未检索到「古诗朗读音色选择」的学术综述或行业硬标准，因此「诗人自己的声音」是本项目的设计选择，不是既定惯例。[cite:15]行业惯例证据不足

性别 × 留白：一个需要诚实说明的空白

本项目人物刻意「减笔、背影、无五官」，靠轮廓与姿态表达。一个自然的疑问是：配音性别会不会过度具象化人物身份，反而损害留白意境？

没有检索到支持「人声性别越模糊越留白」的直接学术证据，也没有找到「男声更适合思乡/孤寂」的权威论述——现有材料只是音色特质的常识性描述（男声浑厚低沉、女声清亮柔和）。因此这个问题不能靠文献裁决，只能作为设计判断：证据缺口

  • 建议取平衡解：用男声（与剪影的男性身份一致），但避免夸张的「苍老诗人」或硬朗「朗诵腔」；目标是中年、低语、慢速、略带孤独、留白感强的声音。
  • 理由是：性别提供了最低限度的身份锚点（「我」是男性），而音量、语速、停顿与情感风格承担留白——不把「李白是谁」讲满。
05

落地路径：改为「预生成音频」

项目是固定文本（四句诗），不是实时交互——这消除了延迟约束，可以直接选质量最高的方案。

建议

把配音从「浏览器实时合成」改为离线预生成音频文件（mp3/wav）再嵌入 HTML。固定文本 + 无延迟要求 = 可以慢慢生成、反复挑音色、逐句精调，且产物可版本化、可回归（与项目「可度量」原则一致）。

推荐阶梯（按成本递增、质量递增）

第 1 步

edge-tts 预生成 — 零成本验证

用 zh-CN-YunxiNeural / YunjianNeural 各生成一版，逐句生成（而非整首一次），人工比对音色气质。

优点：免费、无需 key、几分钟出结果，可立即替换掉扁平的原型。

缺点：仍无句级情感与韵律控制，只是音色比系统默认好。

第 2 步

Azure SSML 逐句合成 — 句级情感 + 句级抑扬顿挫

按句拆分，每句单独套 <mstts:express-as> 风格与 <prosody> 参数：起句 neutral / 承句 lonely 更慢更轻 / 转句音高微扬 / 合句 sad 最慢最低；句间用 <break> 精确控制停顿。优先试 Yunyi（poet）与 Yunhan（lonely + whispering）。

优点：同时解决情感与句级抑扬顿挫，且参数全部显式可记录，能进项目评估链。

缺点：需 API key；中文风格标签须逐音色实测；仍做不到逐字平仄。

第 3 步

（可选）真人吟诵或韵律后处理 — 追求真正的「韵味」

逐字平仄无开箱方案。若句级方案仍觉「没韵味」，两条路：(a) 采录/授权一段真人吟诵，作为最终方案（唯一真正具备拖腔、入声、平长仄短的来源）；(b) 自研韵律后处理（生成整句 → 用声学工具改写音高/时长曲线），风险是机械感。

优点：唯一能真正还原吟诵韵味。

缺点：前者不可规模化且涉版权；后者需自研工具链，属研究性投入。

06

证据缺口与结论

必须声明的证据缺口

  • 没有古诗朗读的 TTS 横向评测。检索未发现对 Azure / 火山 / MiniMax / CosyVoice 在古诗朗读上表现的第三方可复现评测。相关线索仅有 Audio Turing Test（arXiv 2505.11200），其评测维度含「Classical Chinese Poetry/Prose」，但不足以形成排名。[cite:13]证据缺口
  • 「性别模糊是否更留白」无文献支撑。见 §4，只能作为设计判断。
  • Intoner 的可用性未证实。论文存在，但未找到开放 API 或可下载模型。[cite:4]

因此「哪条方案在古诗上更好听」这个问题的最终答案，只能靠本项目自建小样本听测（4 句诗 × 4–6 个候选音色，重点听停顿、尾音、节奏、情感变化）——这恰好与项目「先可度量」的原则一致。

结论

  • 情感：可解，且可逐句。Azure express-as 或 CosyVoice instruct 足以表达起承转合。
  • 抑扬顿挫：句级可解（Azure SSML 的 pitch / contour / break / emphasis）；逐字平仄是行业天花板，无商用 API 支持，需真人吟诵或自研后处理。
  • 性别：男声资源充足；Azure Yunyi 的 poet 风格与 Yunhan 的 lonely+whispering 最对口。目标气质：中年、低语、慢速、留白感强。
  • 工程：改为「离线预生成音频」模式；路径按 edge-tts（零成本验证）→ Azure SSML（情感 + 句级韵律）→ 真人吟诵（韵味） 递进。
